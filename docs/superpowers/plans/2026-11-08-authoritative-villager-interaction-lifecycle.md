# Authoritative Villager Interaction Lifecycle — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement task by task. Also use `superpowers:systematic-debugging`, `superpowers:test-driven-development`, and `minecraft` for focused RED/GREEN verification. Review this plan before implementation.

**Goal:** While an MCA dialogue screen is open, the villager faces the interacting player, approaches a reachable position 2–3 blocks along that player's horizontal look direction (1 block as fallback), and does not leave for work, chores, or sleep. Danger immediately ends the interaction and closes the correct screen. Right-clicking a sleeping villager wakes them.

**Architecture:** Add one MCA `INTERACT` Brain activity, backed by the existing `EntityCommandHandler` player/`interactionId` ownership and `InteractTask`. Reuse the existing `DialogueEngine` session/token authority and `OpenGuiRequest.Type.CLOSE` network type. Keep vanilla/MCA movement, look, and body controls authoritative for physical motion and presentation; the interaction owns their *targets*, not the entity's yaw each tick. Preserve defensive behavior and the normal schedule. Avoid a second interaction-state map, custom AI tick loop, replacement navigation, or temporary schedule copy unless a RED test proves one is necessary.

**Tech stack:** Minecraft 1.21.1, Java 21, MCA common code, Fabric/NeoForge, NeoForge GameTests. Relevant baseline: `InteractTask` matched `origin/1.21.1`; source evidence supports AI ownership conflicts, but the observed head snap still needs runtime reproduction.

**Prerequisite:** This named worktree currently has extensive unrelated changes and unresolved merge conflicts (including `InteractScreen.java`, `VillagerEntityMCA.java`, and `VillagerCommandHandler.java`). Resolve/reconcile those independently before expecting compilable RED tests. Preserve all existing changes and the October dialogue plans. Do not treat compilation failure from conflict markers as a regression test.

## Contract and ownership

- **Begin:** A successful server-side dialogue-screen interaction becomes the single active villager interaction owner, with the already-generated `interactionId`. Reject entry during danger. If asleep, wake the villager on the accepted right-click; vanilla 1.21.1's normal `Villager.mobInteract` does not do this. Cover MCA's `interactAt` and `mobInteract` routes without causing duplicate openings. Resolve any existing owner's navigation intent before issuing a new conversation target; invalidate or safely close a superseded screen without ever letting its late packet release the new owner.
- **While open:** Activate `ActivitiesMCA.INTERACT`. It excludes WORK, REST, IDLE, and CHORE activity packages, without clearing the assigned chore. **CORE remains active in vanilla Brain:** explicitly gate conflicting CORE producers (`FollowTask`, `StayTask`, POI/trading movement, casual look selection, guard movement when not fighting) while keeping the CORE look/move *consumers*, swimming, doors, and real defensive detection operational. Do not let a transient `hurtMarked`, water, or assigned chore toggle conversation off/on. Reuse the same look target while the owner remains valid; clear only interaction-owned `WALK_TARGET`/`LOOK_TARGET` by identity, never another activity's target.
- **Natural head/body motion:** Turn the **head/eyes** smoothly toward the owner using native `LookControl` / `LookAtTargetSink`; do not set `yHeadRot`, `yBodyRot`, or entity yaw abruptly each tick. While walking, the **body faces the path** and the head only tracks the player within `getMaxHeadYRot()` (and normal pitch limits), rather than twisting 180° backward. Once stationary, let the **body gradually follow** the head toward the player; maintain eye contact without head-centering snaps when navigation finishes. Validate MCA's existing `MCABodyRotationControl` (including armed guards) against vanilla `BodyRotationControl` before altering rotation code. No forced cinematic posing or body lock during combat.
- **Approach:** Use a horizontally normalized player look vector. Choose a standable, collision-safe, navigably reachable point at 2–3 blocks in front of the player; try 1 block when the preferred range is unavailable. Treat the player's own hitbox, other entities, hazards/edges, doorways, narrow passages, water and height changes as real constraints; never push through the player just to occupy the mathematically ideal point. If already comfortably positioned, don't pace away just to satisfy a point. Hold a chosen destination until reached, obstructed, or materially changed, with bounded retries/cooldown for unreachable paths. If none can be reached safely, stay put and keep looking at the player. Never teleport or repeatedly restart paths; the existing CORE `WanderOrTeleportToTargetTask` has optional teleport logic, so explicitly prevent it from teleporting for interaction-owned targets.
- **Danger:** Panic, active attack target, or equivalent shared danger takes precedence on the server that tick. End the affected `DialogueEngine` session/offer (do **not** pause for later resumption), release the matching owner, and send an interaction-ID-qualified CLOSE to the client. A delayed close/leave packet must never close a newer or another player's interaction.
- **Normal end:** Closing, trading, disconnecting, player/villager death, changing dimensions, moving out of usable interaction range, or losing the entity releases ownership and restores the appropriate scheduled/chore behavior. A bounded server-side owner-validity check must prevent abandoned GUI ownership persisting indefinitely; `player.containerMenu != null` alone is not proof that an MCA screen is open. A new interaction gets a new ID; opening another villager or re-opening the same one cannot strand the old owner. Client screen removal retains existing normal pause semantics where appropriate; danger uses terminal end semantics.
