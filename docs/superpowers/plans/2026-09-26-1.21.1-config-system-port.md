# 1.21.1 Native Config Port — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan inline task-by-task.

**Goal:** Replace MCA's legacy JSON/custom-sync configuration path with native NeoForge `COMMON`/`SERVER`/`CLIENT` specs on 1.21.1, with Forge Config API Port only on Fabric, migration from the `dev/1.21.1` version-2 `mca.json` schema only, and the searchable native configuration UI.

**Architecture:** `Config` owns three native specs and typed holders: `Config.COMMON`, `Config.SERVER`, and `Config.CLIENT`. Gameplay reads those native config values directly. NeoForge supplies the native implementation; Fabric supplies the compatible implementation through Forge Config API Port. No `ConfigSpecBridge`, no reflected schema, no custom MCA config packet.

**Tech Stack:** Java 21, Minecraft 1.21.1, Fabric Loader 0.19.5, Fabric API 0.116.17+1.21.1, NeoForge 21.1.251, Forge Config API Port 21.1.3, JUnit 5.

**Spec:** `docs/superpowers/specs/2026-09-26-1.21.1-config-system-port-design.md`

## Global Constraints

- Current 1.21.1 option names/defaults and gameplay behavior are authoritative.
- `COMMON` is local on client/server and not synced; `SERVER` is server/world-owned and synced to clients; `CLIENT` is physical-client-only.
- Forge Config API Port is Fabric-only. No Fuzs imports/dependencies under common or NeoForge.
- Only the `dev/1.21.1` version-2 `config/mca.json` schema is migration input; older/fork-only config schemas are ignored, and the source file is never deleted or rewritten.
- Legacy values must not become `ModConfigSpec` defaults.
- The 16 settings formerly synchronized by `ConfigResponse` belong to native `SERVER` config, but they are not the complete SERVER boundary: all safe gameplay/world authority belongs in SERVER.
- Values that must remain installation-local or secret (notably AI credentials/endpoints/prompts) must not be placed in SERVER because NeoForge synchronizes the complete SERVER config to clients.
- Pure rendering/UI preferences belong in CLIENT; `useSquidwardModels` must not alter physical entity dimensions.
- Villager-specific Inworld character assignments are world data, not installation-global config; keep only the private Inworld token in COMMON.
- Chat-AI enablement/model/tool policy/context permission and player trait-bypass policy are SERVER-owned; private endpoint/token/prompt/backend behavior remains COMMON-owned.
- Fabric `CLIENT` registration happens from the client entrypoint only.
- Preserve the `9c3e47c27` searchable native config UI behavior; do not replace native value widgets.
- Keep UI enhancements narrow: searchable nested/list values and tooltips, responsive rows, native numeric controls, readable enums/restart badges, draft-safe list validation and read-only remote SERVER settings. Do not add a two-column map editor or per-setting dirty markers in this pass.
- Use TDD for remaining behavior fixes and fresh verification before completion claims.

## Review Focus

- A non-default legacy JSON value must migrate while Reset still restores MCA's real default.
- Existing TOML must remain authoritative over stale legacy JSON.
- Fabric dedicated server startup must not load/register `mca-client.toml` or client config-screen classes.
- Remote server settings must arrive through native SERVER synchronization without MCA's old config packet.
- Complex list/map values, especially `EquipmentSet` and UUID maps, must survive migration and native validation without type loss.
