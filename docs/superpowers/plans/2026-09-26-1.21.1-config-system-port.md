# 1.21.1 Forge Config Spec Port — Implementation Plan

**Goal:** Port the 26.1.2 config-spec system and its searchable native configuration UI to `dev/1.21.1`, while keeping Forge Config API Port strictly Fabric-only at runtime and preserving every current 1.21.1 setting/default.

**Design:** `docs/superpowers/specs/2026-09-26-1.21.1-config-system-port-design.md`

**Source behavior:** `fork/26.1.x-config-alpha` commit `9c3e47c27`.

**Target base:** `dev/1.21.1` at `aeb3954d7ce0e2a61800140d97c62c3197e28ee4`.

**Versions:** Java 21, Minecraft 1.21.1, Fabric Loader 0.19.5, Fabric API 0.116.17+1.21.1, NeoForge 21.1.251, Forge Config API Port 21.1.3.

## Locked constraints

- Port behavior selectively; do not cherry-pick the alpha commit or replace current `Config.java` wholesale.
- Current 1.21.1 field names/defaults are authoritative.
- Forge Config API Port is a Fabric dependency only. No `fuzs.forgeconfigapiport` coordinate or import under `common` or `neoforge`.
- Scope the Fuzs repository to the Fabric module as well.
- Shared common code compiles against NeoForge 21.1.251's native config/config-screen API; Fabric supplies the compatible API at runtime through Forge Config API Port.
- Preserve `Config.getInstance()` as the one gameplay-facing config state and keep `CommonConfig` sync behavior unchanged.
- Active file becomes `config/mca-common.toml`; legacy `config/mca.json` is import-only and never deleted.
- Port the `9c3e47c27` `ConfigScreenSearch` UI behavior. Do not substitute the later dependency-free `MCAConfigScreen` from `9a31c4e0f`.
- Treat Fuzs `armored-foes` `origin/1.21.1` as supporting dependency-boundary evidence only: it requires Forge Config API Port on Fabric and not on NeoForge, but its Puzzles Lib `ConfigHolder` abstraction is not an MCA dependency or architecture requirement.
- No speculative framework, repository/service layer, custom TOML parser, duplicate schema, or duplicate loader UI.
- Use TDD for behavior changes. Keep new visibility minimal and avoid test-only production abstractions.
- Before completion, run the four `java-code-review-cleanup` passes over one fixed final Java diff/file set: reuse, quality, correctness, efficiency.


### Production implementation

1. Port the useful `ConfigEntry` metadata from `9c3e47c27`: category, optional comment, numeric min/max, and world-restart metadata. Do not copy map key/value type members; derive collection generic types from the actual fields.

2. Annotate the current target `Config.java`; do not copy the historical field list. Preserve every current name/default.

3. Explicitly classify the target-only fields:

   - `archerEquipment`
   - `defaultHeadstoneType`
   - `enableMourning`
   - `giveAdvancementBooks`
   - `guardEquipment`
   - `unSafeBlocksToTeleportOn`
   - `villagerChatAIContextPermissionLevel`
   - `villagerChatAIFuseSystemPrompt`
   - `villagerFollowRange`
   - `villagerPathfindingCheckAllNodeCollisions`
   - `villagerPathfindingCollisionCheckBlocks`
   - `villagerPathfindingDistance`

4. Port `ConfigSpecBridge` behavior, but clean up the alpha structure:

   - build one deterministic ordered `ModConfigSpec`;
   - cache one immutable private binding record per field (`Field`, metadata, config value) during schema construction;
   - do not keep parallel metadata maps or call `Config.class.getField(...)` on each load/save;
   - derive `List<T>` and `Map<K, V>` types once from `Field.getGenericType()` and reject raw/unresolved collections;
   - support only explicit known scalar types plus the current list/map shapes;
   - preserve alpha map serialization ordering and UUID-key conversion, but use binding-aware validators instead of merely checking that a map entry contains `=`;
   - add one explicit `EquipmentSet` map-value adapter for `guardEquipment` and `archerEquipment`, encoded as `<key>=<mainHand>|<offHand>|<head>|<chest>|<legs>|<feet>`;
   - preserve each equipment slot string verbatim and validate only the encoded shape/arity, not registry presence, so optional-mod item ids remain valid configuration;
   - throw a descriptive schema-construction exception for unsupported annotated types instead of stringifying them;
   - on load conversion failure, preserve the existing/default target value and log field + cause;
   - make `saveFrom(...)` return failure when any binding/spec write fails.

5. Keep field iteration/conversion logic simple: guard clauses/plain loops where validation or skipping occurs; deterministic stream sorting is acceptable where it is clearer.

## Task 3 — Replace active JSON persistence with safe one-time migration

**Modify:**
- `common/src/main/java/net/conczin/mca/Config.java`

**Create:**
- `common/src/test/java/net/conczin/mca/ConfigMigrationTest.java`

### RED tests

Cover:

- legacy JSON imports when TOML is absent;
- existing TOML suppresses JSON import;
- invalid JSON leaves the legacy file untouched and falls back safely;
- missing newly-added fields retain current 1.21.1 defaults;
- unknown removed JSON fields remain harmless;
- legacy import does not recreate/rewrite JSON as active storage.

Use temporary paths/files in tests; never touch the developer's real `./config` directory.

### Production implementation

1. Define explicit names:

   ```java
   public static final String CONFIG_FILE_NAME = "mca-common.toml";
   public static final String LEGACY_CONFIG_FILE_NAME = "mca.json";
   ```

2. Split default singleton construction from legacy loading. Static `Config` initialization must no longer write JSON.

3. Keep legacy Gson read behind a narrow helper using try-with-resources. Preserve the original exception cause in concise logs that name `mca.json`.

4. Legacy precedence:

   - TOML present -> never import JSON;
   - TOML absent + JSON present -> load JSON into current `Config`, run `autocomplete()`, write to spec/TOML;
   - invalid JSON -> keep source file, use defaults, log clearly.

5. Keep saving loader-neutral. `Config.save()` calls `autocomplete()` and then `ConfigSpecBridge.saveFrom(this)` directly; it no longer opens a JSON writer and no `PlatformHelper.saveConfigSpec(...)` method is added.

## Task 4 — Wire loader lifecycle without duplicating schema logic

**Create:**
- `fabric/src/main/java/net/conczin/mca/fabric/ConfigHelper.java`

**Modify:**
- `fabric/src/main/java/net/conczin/mca/fabric/MCAFabric.java`
- `neoforge/src/main/java/net/conczin/mca/neoforge/CommonNeoForge.java`

### Fabric

Adapt the historical v5 calls to the locally verified 1.21.1 v4 API:

```text
fuzs.forgeconfigapiport.fabric.api.neoforge.v4.NeoForgeConfigRegistry
fuzs.forgeconfigapiport.fabric.api.neoforge.v4.NeoForgeModConfigEvents
```

`ConfigHelper.register()` owns only loader registration/lifecycle:

- capture `Config.shouldImportLegacyConfig()` before registration;
- register loading/reloading listeners for MCA;
- register `ConfigSpecBridge.SPEC` as `ModConfig.Type.COMMON` with `mca-common.toml`;
- import legacy JSON once from the synchronous loading callback when the captured flag was true, otherwise load spec into the singleton;
- avoid a second schema or parser;
- keep any import-once mutable flag private to this helper and no broader than required by event timing.

Forge Config API Port 21.1.3 loads non-server configs synchronously inside `NeoForgeConfigRegistry.register(...)` and fires the loading callback there. Do not copy the alpha's second unconditional `loadOrImport(...)` call after registration.

Call registration early in `MCAFabric.onInitialize()` before gameplay systems read config.

### NeoForge

Use native constructor injection of `IEventBus` + `ModContainer` in `CommonNeoForge`:

- `modContainer.registerConfig(ModConfig.Type.COMMON, ConfigSpecBridge.SPEC, ConfigSpecBridge.FILE_NAME)`;
- listen for native `ModConfigEvent.Loading` / `Reloading`;
- use the same migration/load bridge;
- no Fuzs classes/imports.

### Porting rule

Use `9c3e47c27:common/src/main/java/net/conczin/mca/client/gui/ConfigScreenSearch.java` as the behavioral source. Preserve its UX:

- `ConfigurationSectionScreen` subclass, not a custom replacement editor;
- persistent query across nested category navigation;
- header search field, hint, tooltip, clear button;
- total/category result summary;
- category match counts;
- recursive section filtering;
- matching over key, translated name, tooltip/comment, scalar value;
- `true/on` and `false/off` boolean aliases;
- section-cache clear + rebuild only when normalized query changes;
- scroll reset after a changed query;
- native option widgets/validation/reset/navigation remain owned by NeoForge/Forge Config API Port.

Do not copy the unused alpha four-argument `matches(...)` overload unless adaptation makes it genuinely necessary. Do not port `9a31c4e0f`'s custom `MCAConfigScreen` row editor.

### API adaptation

Compile common against NeoForge 21.1.251. Adapt mapping/API names proven by compilation/local sources rather than guessing.

The already-verified constructor split is:

- NeoForge native: `ConfigurationScreen(ModContainer, Screen, Filter)`;
- Fabric port 21.1.3: `ConfigurationScreen(String modId, Screen, Filter)`.

Fabric registers its factory with v4 `ConfigScreenFactoryRegistry`; NeoForge registers `IConfigScreenFactory` natively.

### Translations

Merge, do not replace, the alpha config UI/category translation keys. Add translations for all target-only settings. Preserve unrelated current language entries.

6. No removed alpha-only field is resurrected.
7. Automated tests/builds and loader/server smoke tests pass.
8. The final Java diff passes reuse, quality, correctness, and efficiency review with no unresolved high-confidence issue.
