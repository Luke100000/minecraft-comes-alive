# Dialogue reply placeholders and asynchronous parchment results Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Show a single disabled three-dot reply row until character reveal is finished, show an indeterminate parchment progress bar during genuine async dialogue operations, and display results (including rumour coordinates) inline via reusable, datapack-configured resolvers.

**Architecture:** Keep server-owned session authority in `DialogueEngine` and character reveal in `DialoguePresentation`. Add optional typed `resolve` on a dialogue node, a server-thread-scoped resolver registry plus correlated pending/ready messages; replace only the dialogue rumour's deferred `location` command with a node resolver. Keep non-dialogue location command behavior intact.

**Tech Stack:** Minecraft 1.21.1, Java 21, shared Fabric/NeoForge, Mojang `Codec` / `StreamCodec`, CompletableFuture/CompletionStage, existing 9-sliced GUI.

**Spec:** `docs/superpowers/specs/2026-11-09-dialogue-pending-and-async-design.md` — **P4 approved**, including the generic addon-registerable resolver. This plan supersedes the rumour-specific `mca:rumor_location` action in `docs/superpowers/plans/2026-11-09-inline-location-rumors.md`.

## Global Constraints

- Follow approved **Character reveal** and **Rumours search** variants; retain **40 ms per Unicode grapheme**. Do not insert a minimum wait or force instant text.
- One disabled grey three-square row while choices/Continue/Finish are unavailable. An indeterminate **parchment** bar appears only for server-confirmed true async operations, never for normal text reveal.
- New async event feature is optional and strictly decoded from `data/<namespace>/dialogue_events/*.json`; normal existing packs remain compatible. No arbitrary JSON scripts or commands.
- Results, lifecycle and rewards stay server-authoritative. Addon resolvers are namespaced and registered via Java during initialization. Results are shown in parchment, **never vanilla chat**, for the dialogue location path.
- Retain Java 21, Minecraft 1.21.1, existing common multiloader networking, scrolling, skin textures, history, HUD clearance and client-side physical separation. No new dependencies or worktrees.
- Preserve unrelated dirty changes already present in `InteractScreen.java`, `DialogueOverlayLayout.java`, their tests, and unrelated 2026-11-09 plans.
- Design approval is already granted for the generic P4 resolver. P2 owns in-progress UI/presentation work and P4 backend owns its code integration; coordinate shared interfaces and file ownership. The current reconciliation edits only this plan and its companion spec, with no code, Gradle or commits.
- Built-in location successes preserve `villager.getTranslatable(player, "dialogue.location." + structureId.getPath(), coords)`: the method supplies player name as `%1$s` and coordinates as `%2$s`. Fallback is `villager.getTranslatable(player, "dialogue.location.forgot")`, never a fabricated location key or vanilla-chat output. Keep non-dialogue `location` command behavior, configured structure pool and existing route weights.

## Review Focus

1. **Duplicate, delayed or out-of-order callbacks** must not reveal an old result or duplicate effects; cancellation of the dialogue's operation-unique locator UUID must not cancel a separate search owned by the villager UUID (Tasks 2 and 5: `staleAsyncCompletionsAreDiscarded`, `dialogueLocatorOwnerDoesNotCancelLegacyLocation`).
2. **Close, pause, reload or shutdown during lookup** must terminate pending UI/state; explicit Resume may restart an idempotent lookup under a fresh token (Task 2: `leavingOrReloadingCancelsPendingWork`).
3. **Empty pool, unknown structure or provider exception** must show a localized fallback, not get stuck or claim fake coordinates (Tasks 1, 2, 5: `invalidResolveConfigIsRejected`, `failedAsyncOperationResolvesToFallback`, `emptyRumourPoolShowsFailure`).
4. **Non-async lines with no choices or only Finish** must show only one placeholder during reveal, then the proper action, without changing history (Task 4: `typingOnlyNodeHasOnePlaceholderUntilComplete`).
5. **Client dedicated-server boundary / codec size / unrecognized provider type** must fail safely without side-only class loading or incompatible loader registration (Tasks 1, 3: `unknownResolveTypeIsRejected`, `pendingPacketCodecRoundTrip`; final Fabric/NeoForge dedicated-server smoke test).

### Cross-task contract

- `DialogueAsyncResolver.Result(boolean found, Optional<String> lineOverride, List<String> arguments)` with factories `withKey(String key, String... arguments)`, `found(String... arguments)` and `missing()`. `DialogueAsyncResolver.resolve(DialogueContext context, UUID operationId) : CompletionStage<Result>` and `DialogueAsyncResolver.cancel(UUID operationId)` form the resolver lifecycle. The addon interface is `Provider<T>.resolve(T parameters, DialogueContext context, UUID operationId) : CompletionStage<Result>` plus default `Provider<T>.cancel(T parameters, UUID operationId)`. `DialogueAsyncResolver.register(ResourceLocation id, Codec<T> codec, Provider<T> provider)` is available before datapack reload; reject duplicate/built-in IDs. Only read-only, idempotent providers are allowed in v1. Validate nonblank `lineOverride` keys.
- `DialogueEvent.Node.resolve() : Optional<DialogueAsyncResolver>` contains the typed resolver, its parameters, `pendingLine()` and `failureLine()`. Success uses the node's `line` or an explicit resolver-supplied dynamic `lineOverride` with string arguments; missing/failure uses `failureLine()`. Single-line node only. Preserve existing `DialogueEvent.Node` constructor overloads and `fromFields`/strict `validateKnownFields` behavior for legacy tests/pack data.
- `DialogueEngine.DialogueDisplay` is a sealed view: `Ready(DialogueNodeView view)` or `Pending(DialoguePendingView view)`. `DialoguePendingView(UUID sessionId, long offerToken, Component pendingLine)`. Transition `view()` becomes `display()`; selectors return an optional display instead of an optional ready-only view. Keep existing rejection/paused/ended statuses.
- `DialogueEngine` owns a pending ticket keyed by player UUID and bound to player/villager UUIDs, session UUID, token, reload generation, node ID and line index, plus a fresh `UUID.randomUUID()` operation identity and the `DialogueAsyncResolver` instance. On completion, it marshals to the **server thread**, validates the still-current ticket and player/villager/world/interaction owner, then sends a normal `InteractionDialogueNodeResponse.active` with a resolved Component. Use `context.villager().getTranslatable(context.player(), key, args...)` on that thread; `Component.translatable(key, args...)` alone would miss the implicit player argument and MCA dialogue variant prefixes. `InteractionDialoguePendingResponse` conveys `sessionId`, `offerToken` and localized `pendingLine`; no spoofed percentage.
- Every `mca:structure_location` operation uses the engine-supplied operation UUID as its locator owner. `AsyncStructureLocator.locate(owner, level, origin, HolderSet, 64)` replaces same-owner work and completes on the server executor; the built-in `resolver.cancel(operationId)` calls `AsyncStructureLocator.cancel(owner)` on the server thread, canceling exactly that request and releasing its chunk ticket. Do **not** pass or cancel `villager.getUUID()`, which is the owner used by the existing `VillagerCommandHandler` location command.
- Client `DialoguePresentation.acceptPending(InteractionDialoguePendingResponse)`, `pendingAsync()` and `pendingLine()` expose the genuine pending phase; `awaitingReply()` and `revealingLine()` expose presentation-only waiting and typing. `acceptNode` clears matching pending state and rejects older packets; `pause`/`clear`/`beginRequest` clear stale pending UI.

## Concrete integration order and shared-file ownership

1. **P4 backend, schema first.** Register built-in/addon resolver codecs before datapack reload. Extend `DialogueEvent.validateKnownFields`, `Node.CODEC`/`fromFields` and validation for optional `resolve`. Keep existing events and constructor call sites valid. Verify resolver registration/parse behavior independently.
2. **P4 backend, lifecycle second.** Add the pending ticket to `DialogueEngine` and hook node entry after `resolveAutomaticTransitions` in initial selection, resumed selection, choice and advance. Generate the operation UUID and install the ticket with its resolver **before** invoking `resolver.resolve(context, operationId)`/attaching callbacks. Pending nodes cannot be advanced, chosen, auto-committed or acted on. Resume creates a fresh token/ticket. Invalidate the current ticket before calling `resolver.cancel(operationId)` on the server thread; marshal even immediate/exceptional future completion to server thread, validate all identities, and enforce 600 ticks using existing `tick`. Inspect the special single-line slap terminal branch so it cannot bypass pending resolution.
3. **P4 backend, protocol third.** Extend the current `select(): Optional<DialogueNodeView>` and `choose()/advance(): TransitionResult` call paths to distinguish rejected, pending and ready without treating pending as rejection. Adapt `InteractionDialogueSelectMessage`, shared `InteractionDialogueChoiceMessage.sendTransition` (also used by `InteractionDialogueAdvanceMessage`), and register the pending S2C payload in `MessagesMCA` with a corresponding `ClientHandler` entry. Reuse `InteractionDialogueNodeResponse.active` for ready. Correlate both pending and ready to the same session/offer token and **dispatch pending before ready**, including synchronously completed futures, without a display-time delay. Reject stale/duplicate packets.
4. **P2 UI handoff after the protocol seam is agreed.** P2 owns `ClientHandlerImpl.DialoguePresentation`, `InteractScreen` and any required `DialogueOverlayLayout` changes. Integrate the new pending payload with its shared pending/typing state before any P4 backend edits to a P2-owned file. Use one non-clickable three-square row and a parchment progress bar only for server-confirmed async, then character-reveal the ready line before enabling all choices/Finish. Do not have separate P4 and P2 implementers concurrently edit `ClientHandlerImpl`.
5. **P4 backend, built-in and migration last.** Add `mca:structure_location` with the operation-unique locator owner, preserve `Config.structuresInRumors`, registered-structure choice, random origin offset `1024/0` and radius `64`. Use dynamic `dialogue.location.<structurePath>` on success and `dialogue.location.forgot` on failure through `getTranslatable`. Change only the two location outcomes in `social/rumors.json` by removing deferred `mca:command location` actions and adding `resolve` to the existing `location` visible node. Keep all weights/requirements, lore/failed branches, cooldown and history. Retain the legacy gameplay command untouched. Update the three user guides and verify both loaders and the combined client flow after the separately owned changes are integrated.

The two older rumour-only documents remain as superseded historical proposals. Do not add `DialogueAction.RumorLocation` or `mca:rumor_location`, fork a second lookup pipeline, or overwrite the P2 work.
