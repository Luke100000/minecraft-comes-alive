# 1.21.1 Forge Config Spec Port — Design

Date: 2026-09-26

Status: proposed design; implementation remains blocked until this spec and its plan are reviewed.

## Goal

Port the useful configuration-system work from `fork/26.1.x-config-alpha` into the current `dev/1.21.1` line without regressing newer 1.21.1 settings.

The resulting 1.21.1 configuration path must:

- replace the hand-written `mca.json` persistence path with `ModConfigSpec`-backed `mca-common.toml`;
- preserve automatic import of an existing legacy `config/mca.json`;
- use NeoForge 21.1.251's native configuration implementation on NeoForge;
- require Forge Config API Port only for the Fabric runtime/mod path;
- use one shared configuration schema and one shared MCA `Config` object rather than maintaining loader-specific copies;
- expose the native-style configuration screen on both loaders, including the searchable section UI from the historical alpha;
- preserve all configuration fields currently present on `dev/1.21.1`.

This is a configuration-infrastructure port. It must not change gameplay semantics or default values except where the config system itself requires a representation change.

## Source and target authority

### Target

The target branch is the current `dev/1.21.1` state at base commit `aeb3954d7ce0e2a61800140d97c62c3197e28ee4`.

Version authority comes from its build files:

- Minecraft: `1.21.1`
- Fabric Loader: `0.19.5`
- Fabric API: `0.116.17+1.21.1`
- NeoForge: `21.1.251`

The target branch's current `Config.java` is authoritative for the set of options, defaults, field names, and gameplay-facing accessors.

### Historical behavior source

`fork/26.1.x-config-alpha` at commit `9c3e47c27` is the behavioral source for the Forge/NeoForge config-spec migration. It introduced:

- `ConfigEntry` metadata annotations;
- `ConfigSpecBridge`;
- TOML migration and legacy JSON import;
- loader-specific config registration;
- `ConfigScreenSearch`;
- config-screen integration for Fabric and NeoForge;
- translation metadata for config categories and entries.

`fork/26.1.x-config-alpha-no-dependencies` at commit `9a31c4e0f` is reference material only. It explicitly describes itself as not stable and replaces the native config-spec flow with a custom schema/screen. It is not the behavioral authority for this port.

## Dependency boundary

The user-facing dependency rule is:

> Forge Config API Port is a Fabric runtime/mod dependency only. NeoForge must use its own native config implementation and must not require or load Forge Config API Port.

To avoid duplicating the shared spec builder and searchable screen, `common` compiles against NeoForge's official 1.21.1 API as `compileOnly`. Forge Config API Port intentionally mirrors the relevant NeoForge config API on Fabric, so the same common bytecode can run against the Fabric compatibility implementation. This keeps Fuzs dependencies completely out of `common` and `neoforge`.

The intended dependency shape is:

```text
common
  compileOnly net.neoforged:neoforge:21.1.251
  -> official NeoForge config/config-screen API at compile time only

fabric
  modImplementation fuzs.forgeconfigapiport:forgeconfigapiport-fabric:21.1.3
  -> required Fabric runtime/mod dependency

neoforge
  no fuzs.forgeconfigapiport dependency
  -> native NeoForge ModConfigSpec / ConfigurationScreen
```

The build must prove this boundary by inspecting both loader runtime classpaths. A successful compile alone is not enough. No `fuzs.forgeconfigapiport` coordinate may appear in `common/build.gradle` or `neoforge/build.gradle`.

## Version-specific adaptation

The 26.1.2 alpha used Forge Config API Port v5 Fabric APIs. The locally available 1.21.1 Forge Config API Port `21.1.3` exposes the v4 NeoForge-compatible API:

```text
fuzs.forgeconfigapiport.fabric.api.neoforge.v4.NeoForgeConfigRegistry
fuzs.forgeconfigapiport.fabric.api.neoforge.v4.NeoForgeModConfigEvents
fuzs.forgeconfigapiport.fabric.api.neoforge.v4.client.ConfigScreenFactoryRegistry
```

The port must adapt to those v4 names and signatures. Do not copy the 26.1.2 v5 imports verbatim.

NeoForge 21.1.251 already supplies:

```text
net.neoforged.neoforge.common.ModConfigSpec
net.neoforged.neoforge.client.gui.ConfigurationScreen
```

NeoForge therefore needs no compatibility library.

## Canonical configuration model

`net.conczin.mca.Config` remains the single mutable MCA configuration object used by gameplay code.

The config-spec layer is an adapter around that object, not a second gameplay-facing state model:

```text
Config fields + ConfigEntry metadata
              |
              v
       ConfigSpecBridge
          /         \
         /           \
NeoForge native    Fabric Forge Config API Port
ModConfigSpec      NeoForge-compatible ModConfigSpec
         \           /
          \         /
          Config.getInstance()
```

`CommonConfig` server-sync behavior remains unchanged. Network synchronization must continue to copy server-owned options into `CommonConfig` exactly as it does now.

## Configuration metadata

Port `ConfigEntry` from the alpha as a small runtime field annotation carrying:

- category;
- comment;
- numeric minimum and maximum;
- map key/value type metadata;
- restart metadata where needed.

The current `Config.java` fields must be annotated against their current names and defaults. Do not replace the current file with the historical alpha version.

The alpha predates several current 1.21.1 options. These target-only fields must be explicitly classified and included:

- `archerEquipment`
- `defaultHeadstoneType`
- `enableMourning`
- `giveAdvancementBooks`
- `guardEquipment`
- `unSafeBlocksToTeleportOn`
- `villagerChatAIContextPermissionLevel`
- `villagerChatAIFuseSystemPrompt`
- `villagerFollowRange`
- `villagerPathfindingCheckAllNodeCollisions`
- `villagerPathfindingCollisionCheckBlocks`
- `villagerPathfindingDistance`

The historical `villagerPathfindingBlacklist` field no longer exists in the target architecture and must not be resurrected.

Every public persisted config field must have exactly one schema entry. A test must fail if a new persisted field is later added without `ConfigEntry` metadata.

## `ConfigSpecBridge`

Port the alpha's `ConfigSpecBridge` concept, but revalidate it against 1.21.1 APIs and the current config surface.

Responsibilities:

- build one `ModConfigSpec` from `ConfigEntry` metadata;
- retain deterministic category and field ordering;
- map booleans, integers, longs, floats/doubles, strings, lists, and maps to supported config-spec values;
- preserve numeric range metadata;
- convert map fields to and from the TOML-safe list representation used by the alpha;
- load spec values into the singleton `Config` instance;
- write the current `Config` instance back into the registered spec;
- import the legacy JSON config once when appropriate.

The bridge must remain a serialization/configuration adapter. Gameplay code must continue reading `Config.getInstance()` rather than reading `ModConfigSpec.ConfigValue` objects directly.

Reflection is acceptable here because the config fields are already a flat public schema and the annotation is explicitly the schema declaration. Reflection must be centralized in `ConfigSpecBridge`; loader entrypoints must not repeat field-walking logic.

## File names and migration

The new active configuration file is:

```text
config/mca-common.toml
```

The legacy file is:

```text
config/mca.json
```

`Config` must expose these names explicitly rather than scattering literals.

Migration rules:

1. If `mca-common.toml` exists, it is authoritative. Do not import `mca.json` over it.
2. If `mca-common.toml` does not exist and `mca.json` exists, deserialize the legacy JSON into the current `Config` type, run `autocomplete()`, write those values into the registered spec, and continue using TOML.
3. Leave the old JSON file in place as a recovery artifact. Do not delete or rewrite it during migration.
4. Unknown/removed legacy fields are ignored by Gson as today.
5. Missing current fields receive the current 1.21.1 defaults via `autocomplete()` / normal Java initialization.
6. Invalid legacy JSON logs a clear error and falls back to current defaults without destroying the legacy file.
7. Once the config spec is active, `Config.save()` writes through the registered config-spec path rather than writing JSON.

The static `Config` singleton must not eagerly recreate `mca.json` during class initialization. Loader registration owns activation of the new file format.

## Platform save seam

Reuse the existing `MCA.platformHelper` convention rather than introducing a second service framework.

Add one narrow platform operation equivalent to:

```java
boolean saveConfigSpec(Config config)
```

Fabric delegates to the Fabric config helper. NeoForge delegates to `ConfigSpecBridge.saveFrom(config)` after the native spec has been registered.

`Config.save()` remains the gameplay-facing save entrypoint. It calls `autocomplete()` and delegates through the platform seam. Failure must be logged clearly.

## Fabric lifecycle

Add a focused `fabric.ConfigHelper` that owns Forge Config API Port registration and lifecycle events.

On Fabric initialization:

1. register loading and reloading listeners for MCA;
2. register `ConfigSpecBridge.SPEC` as `ModConfig.Type.COMMON` with file name `mca-common.toml` through `NeoForgeConfigRegistry` v4;
3. perform legacy import only when TOML does not exist and JSON does;
4. otherwise load the registered spec into `Config.getInstance()`;
5. reload events refresh the singleton config from the spec.

`MCAFabric.onInitialize()` calls this registration before gameplay systems can rely on configuration values.

## NeoForge lifecycle

NeoForge registration stays entirely native.

`CommonNeoForge` receives the mod event bus and `ModContainer`, then:

- registers `ConfigSpecBridge.SPEC` as `ModConfig.Type.COMMON` with `mca-common.toml`;
- listens for `ModConfigEvent.Loading` and `Reloading` on the mod event bus;
- imports legacy JSON on the first eligible load;
- otherwise loads spec values into `Config.getInstance()`.

No Forge Config API Port class may be referenced from `neoforge/src`.

## Configuration screen

Port `ConfigScreenSearch` as the shared search/filter extension around NeoForge's `ConfigurationScreen` API.

NeoForge:

- register `IConfigScreenFactory` with `ModContainer`;
- construct native `ConfigurationScreen` for MCA;
- use `ConfigScreenSearch` as the section filter/search integration.

Fabric:

- register a config screen through Forge Config API Port's v4 `ConfigScreenFactoryRegistry`;
- construct the compatibility library's NeoForge-compatible `ConfigurationScreen`;
- use the same `ConfigScreenSearch` implementation.

This keeps one UI behavior instead of maintaining a custom Fabric config screen.

Mod Menu remains optional. It may be present in the development runtime and listed as a Fabric suggestion so the screen is easy to reach, but it is not an MCA required dependency.

## Translations

Port the alpha's configuration category and entry translations into the current `en_us.json`, then add translations for every target-only field listed above.

Translation keys must follow the same scheme used by `ConfigSpecBridge`, for example:

```text
mca.configuration.section.<category>
mca.configuration.<fieldName>
```

Do not replace unrelated current translations with the historical file wholesale.

## Build changes

The build should use one explicit 1.21.1 Forge Config API Port version property, expected to be `21.1.3` based on the locally available version-matched artifact.

Required build changes:

- add the Fuzs Maven repository with group filtering if the direct Fuzs coordinates are used;
- add `forge_config_api_port_version=21.1.3` to `gradle.properties`;
- add NeoForge 21.1.251 as a `compileOnly` API dependency for `common` so shared config-spec and searchable-screen code compiles against the native API surface;
- add Fabric `modImplementation` for `forgeconfigapiport-fabric`;
- expand the Forge Config API Port version into `fabric.mod.json`;
- add Fabric metadata dependency `forgeconfigapiport` with a compatible minimum version;
- optionally add Mod Menu only as a Fabric development/suggested integration;
- add no Forge Config API Port dependency to `neoforge/build.gradle` or NeoForge metadata.

Do not add a direct Night Config dependency unless compilation proves the common API artifact fails to provide the required types. The 26.1.2 alpha carried an explicit Night Config dependency, but the 1.21.1 dependency graph must be inspected before preserving it.

## Error handling and correction

Use the loader/config-spec correction behavior for malformed TOML values rather than adding a second parser.

MCA-specific error handling is limited to:

- legacy JSON import failures;
- reflection/schema mismatches;
- unsupported field types;
- failed explicit saves.

Schema construction errors should fail loudly during development rather than silently dropping a configuration field.

## Testing and verification

### Schema/unit verification

Add focused common tests for behavior that can run without a Minecraft world:

- every persisted `Config` field has `ConfigEntry` metadata;
- current-only settings are represented in the generated schema;
- no removed `villagerPathfindingBlacklist` entry exists;
- list and map conversion round-trip without losing scalar types;
- legacy JSON import preserves representative boolean, numeric, list, map, and newly added 1.21.1 values;
- TOML-present state suppresses legacy import.

Do not add a production abstraction solely to make tests easier.

### Loader build verification

Run:

```powershell
.\gradlew.bat :common:test :fabric:build :neoforge:build --no-daemon
```

### Dependency-boundary verification

Inspect Fabric and NeoForge runtime classpaths. Acceptance requires:

- Fabric runtime contains Forge Config API Port;
- NeoForge runtime does not contain any `fuzs.forgeconfigapiport` module;
- the built NeoForge jar does not embed Forge Config API Port classes;
- Fabric metadata declares Forge Config API Port;
- NeoForge metadata does not.

### Runtime verification

Compilation cannot prove config lifecycle or GUI behavior. Before declaring the implementation complete:

1. run Fabric client with Forge Config API Port installed and open/save the MCA config screen;
2. run NeoForge client and open/save the native MCA config screen;
3. run a dedicated-server startup on at least NeoForge and one Fabric server/runtime path to catch client-only classloading mistakes;
4. exercise one legacy `mca.json` migration on each loader and verify the resulting `mca-common.toml` preserves representative values;
5. restart after migration and verify TOML, not JSON, remains authoritative.

## Port audit requirements

Every meaningful hunk from `9c3e47c27` must receive one explicit outcome during implementation:

- ported;
- adapted for 1.21.1 API differences;
- already present on the target;
- intentionally omitted with a reason.

The implementation must specifically call out:

- v5 -> v4 Fabric API adaptation;
- target-only config fields added since the alpha;
- removal/non-port of `villagerPathfindingBlacklist`;
- dependency differences between common, Fabric, and NeoForge;
- any alpha README/changelog text that is no longer appropriate for 1.21.1.

## Non-goals

- No gameplay default changes.
- No cleanup of unrelated config names.
- No replacement of `CommonConfig` server synchronization.
- No custom dependency-free configuration framework.
- No custom TOML parser.
- No duplicate Fabric/NeoForge configuration schema.
- No resurrection of removed config fields.
- No unrelated UI redesign beyond porting the searchable native config screen.

## Acceptance criteria

The port is complete only when all of the following are true:

1. `mca-common.toml` is the active config file on Fabric and NeoForge.
2. Existing `mca.json` values migrate without deleting the source file.
3. All current 1.21.1 persisted options are represented exactly once in the schema.
4. Fabric requires Forge Config API Port 21.1.3 (or a review-approved equivalent 1.21.1 release).
5. NeoForge has no Forge Config API Port runtime/module dependency.
6. Both loaders present the searchable native-style config screen.
7. Saving through existing MCA code updates the active spec/TOML path.
8. Common tests, Fabric build, and NeoForge build pass.
9. Fabric and NeoForge runtime smoke tests confirm load, save, reload, and legacy migration behavior.
10. The implementation audit accounts for every relevant alpha hunk without overwriting newer target behavior.
