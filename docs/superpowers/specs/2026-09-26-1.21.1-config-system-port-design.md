# 1.21.1 Native Config Port — Design

Date: 2026-09-27

Status: approved architecture, implementation in progress.

## Goal

Replace MCA's hand-written `mca.json` configuration path with the native NeoForge `ModConfigSpec` model on Minecraft 1.21.1 while preserving current settings, defaults, legacy JSON migration, and the searchable native config UI.

The final architecture has one configuration system, split by NeoForge ownership:

- `Config.COMMON` / `Config.COMMON_SPEC` for local settings loaded on both physical sides and never synced;
- `Config.SERVER` / `Config.SERVER_SPEC` for server/world-owned settings automatically synced to clients;
- `Config.CLIENT` / `Config.CLIENT_SPEC` for physical-client-only settings.

There is no `ConfigSpecBridge`, no annotation/reflection schema adapter, no duplicate gameplay config object, and no custom MCA config synchronization packet.

## Version authority

The target checkout is Minecraft `1.21.1`, Java 21, Fabric Loader `0.19.5`, Fabric API `0.116.17+1.21.1`, NeoForge `21.1.251`, and Forge Config API Port `21.1.3`.

Version-matched local NeoForge documentation under `C:/Users/Mik/Downloads/MCA/mc_source_code/Documentation/versioned_docs/version-1.21.1` is authoritative for config type semantics:

- `CLIENT`: physical client only, not network-synced;
- `COMMON`: physical client and physical server, not network-synced;
- `SERVER`: world/server config, loaded for server startup and automatically synced to clients.

The historical `fork/26.1.x-config-alpha` commit `9c3e47c27` remains a behavioral reference for the searchable native configuration UI and legacy migration ideas, not for its rejected bridge architecture.

## Dependency boundary

NeoForge uses its native configuration implementation. Fabric uses Forge Config API Port only as a loader compatibility implementation of the NeoForge config APIs.

```text
common
  compileOnly net.neoforged:neoforge:21.1.251

fabric
  modImplementation fuzs.forgeconfigapiport:forgeconfigapiport-fabric:21.1.3

neoforge
  native NeoForge config APIs only
```

No Fuzs import or dependency may exist under common or NeoForge source/runtime paths.

## Canonical configuration model

`Config` is the static owner of three native specs and their typed holders:

```text
Config.COMMON_SPEC -> Config.COMMON : CommonConfig
Config.SERVER_SPEC -> Config.SERVER : ServerConfig
Config.CLIENT_SPEC -> Config.CLIENT : ClientConfig
```

Gameplay code reads these typed config values directly. A setting is defined exactly once, in the holder matching its ownership.

The old `CommonConfig` Java data object is not a second runtime state model. Its current option set is migrated into native `ModConfigSpec.ConfigValue` fields in the appropriate holder classes.

## Ownership rules

Place a setting in `SERVER` when the server/world owns gameplay behavior and the value is safe to disclose to connecting clients. NeoForge/FCP network synchronization is the one synchronization path. This includes gameplay policy even when the old custom packet never synchronized that option.

Place a setting in `COMMON` only when each installation intentionally owns the value locally and it must not be overwritten by a remote server. Server-local credentials, endpoints, prompts, and other values that must not be disclosed to clients remain unsynchronized rather than moving into `SERVER`, because NeoForge synchronizes the complete SERVER config to clients.

Place a setting in `CLIENT` when it is purely client-side and must never be loaded on a physical dedicated server.

The 16 values previously copied by MCA's `ConfigResponse` are server-owned and therefore belong in `SERVER`, but that historical packet is not the ownership boundary. The final 1.21.1 audit classifies all safe gameplay/world policy as SERVER-owned. After merging current `dev/1.21.1`, the resulting native holders contain 131 SERVER values, 9 deliberately unsynchronized COMMON Chat-AI infrastructure values, and 19 CLIENT values. TTS preferences and credentials are CLIENT-owned and grouped under the client `tts` section. The server-wide voice-mode and notification-delivery switches remain SERVER-owned because `dev/1.21.1` applies those choices while producing server-authoritative sound/message events rather than as per-client presentation overrides.

Villager-specific Inworld character assignments are not configuration. They are persisted as per-save `SavedData`, seeded from legacy `mca.json` mappings when a world first creates that data. This keeps villager UUID state with the world while `inworldAIToken` remains private COMMON infrastructure.

`useSquidwardModels` is a CLIENT rendering preference. It no longer controls physical MCA villager dimensions; physical dimensions are derived from synchronized entity/genetics state so a local renderer choice cannot create client/server hitbox disagreement.

The migration to native `SERVER` synchronization makes `ConfigRequest`/`ConfigResponse` obsolete and they must remain removed.

## Defaults are immutable product defaults

Every `define(...)` call must use MCA's real 1.21.1 default value. Legacy `mca.json` values must never be supplied as the `ModConfigSpec` default supplier/value.

This distinction is required because the native config screen's Reset action and config correction use the spec default. A migrated user value becoming the spec default would make Reset restore the user's old value instead of MCA's product default.

Legacy values are migration input only: after registration/load they are written into the loaded config values and saved, while `ConfigValue#getDefault()` remains the original MCA default.

## File layout and migration

Active files are:

```text
config/mca-common.toml
config/mca-client.toml
<world>/serverconfig/mca-server.toml
```

Forge Config API Port may use the ordinary config directory as the base/fallback for server config exactly as its 1.21.1 implementation specifies; per-world `serverconfig` overrides remain native behavior.

The legacy import source is `config/mca.json`.

Migration rules:

1. Read legacy JSON only when the corresponding native TOML does not already contain migrated MCA state.
2. Deserialize using the current legacy field model so unknown removed fields remain harmless and missing current fields keep current Java defaults.
3. Map each legacy field into its new COMMON/SERVER/CLIENT owner.
4. Set loaded `ConfigValue`s, then save the appropriate native specs.
5. Never delete or rewrite `mca.json`; it remains a recovery artifact.
6. Invalid JSON logs the original cause and leaves native defaults active.
7. Migration does not alter native spec defaults.

Migration helpers may exist in `Config` as a one-time compatibility layer, but they must not remain a parallel active configuration model.

## Loader lifecycle

### NeoForge

`CommonNeoForge` receives `IEventBus` and `ModContainer` and registers:

- `COMMON_SPEC` as `ModConfig.Type.COMMON`;
- `SERVER_SPEC` as `ModConfig.Type.SERVER`;
- `CLIENT_SPEC` as `ModConfig.Type.CLIENT`.

NeoForge owns loading, saving, correction and server-to-client synchronization.

Config reload handling may refresh derived MCA caches such as Destiny destinations, but must not copy native values into a second MCA config state.

### Fabric

`MCAFabric` registers only `COMMON` and `SERVER` through Forge Config API Port's v4 `NeoForgeConfigRegistry`.

`MCAFabricClient` registers `CLIENT`. Forge Config API Port loads non-server configs immediately at registration time, so registering CLIENT from the common Fabric initializer would load/create client config on a dedicated server and is forbidden.

Fabric uses Forge Config API Port's built-in server config synchronization; MCA does not send its own config packet.

## Searchable native configuration screen

Both loaders use the native NeoForge-compatible `ConfigurationScreen` and the shared `ConfigScreenSearch` behavior ported from `9c3e47c27`:

- section-screen subclass rather than a custom value editor;
- persistent query while navigating nested categories;
- search field, hint, tooltip, clear action and result summary;
- category result counts and recursive filtering;
- matching on key, translated name, comment/tooltip and scalar value;
- boolean aliases `true/on` and `false/off`;
- rebuild only when normalized query changes, then reset scroll;
- native validation, Reset, Save and navigation remain owned by NeoForge/FCP.

Fabric registers the screen via Forge Config API Port's v4 `ConfigScreenFactoryRegistry`. NeoForge registers `IConfigScreenFactory` natively.

## Translation and representation rules

Every visible setting receives `mca.configuration.<settingName>` translation metadata and category/section translations as required by the native screen.

Maps unsupported directly by NightConfig are represented deterministically as lists of encoded strings. Validators must parse the actual declared shape, including UUID and `EquipmentSet` maps; malformed entries must be rejected by the native spec correction path rather than partially loaded.

`EquipmentSet` entries preserve all six slot strings verbatim so optional-mod item IDs remain valid configuration data.

## Testing and verification

Behavioral coverage must prove:

- representative defaults for COMMON/SERVER/CLIENT remain the original MCA defaults;
- importing non-default legacy JSON changes current values without changing `ConfigValue#getDefault()`;
- existing native TOML wins over legacy JSON;
- legacy JSON remains untouched;
- all legacy persisted fields map to exactly one current native owner;
- all safe server/world gameplay policy, including the 16 formerly custom-synced values, is in SERVER;
- server-local AI credentials are not exposed through SERVER synchronization;
- villager-specific Inworld character assignments are world-owned saved data rather than COMMON config;
- player trait restrictions are enforced by the server and synchronized as SERVER policy;
- `useSquidwardModels` is CLIENT-owned and does not alter physical entity dimensions;
- removed `villagerPathfindingBlacklist` is not resurrected;
- searchable UI matching/filtering behavior is covered by focused JVM tests where practical.

Verification before completion:

```powershell
.\gradlew.bat :common:test :fabric:build :neoforge:build --no-daemon
rg -n "fuzs\.forgeconfigapiport" common neoforge
rg -n "ConfigSpecBridge|ConfigEntry|ConfigRequest|ConfigResponse" common fabric neoforge
rg -n "villagerPathfindingBlacklist" common fabric neoforge
git diff --check
git status --short
```

Runtime smoke evidence should additionally cover client config-screen access and dedicated-server startup on both loaders. If a runtime lane cannot be completed in the current environment, report that boundary separately from automated/build verification.

## Completion criteria

1. MCA uses native COMMON/SERVER/CLIENT specs as the only active configuration state.
2. Fabric alone depends on Forge Config API Port; NeoForge is native.
3. Legacy JSON migrates once without changing native defaults or deleting the source file.
4. Server-owned settings use native SERVER synchronization; custom MCA config packets are gone.
5. CLIENT config is registered only on a physical client on Fabric.
6. Both loaders expose the searchable native configuration UI.
7. Current 1.21.1 option names, defaults and gameplay semantics are preserved.
8. Automated tests/builds pass and runtime-smoke status is explicitly reported.
