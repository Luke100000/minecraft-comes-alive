# Server-authoritative appearance catalog: incremental-sync design and simplification review

Status: **incremental implementation exists in the worktree, but a simpler design is now proposed for review (2026-10-10)**. The original approved design and its execution evidence are preserved below as history, **not current implementation instructions**. The simplification is not yet implemented or runtime-verified.
Target: `feature/1.21.1-eye-system`, Minecraft 1.21.1, Java 21, Fabric and NeoForge.

## Superseding design proposal (2026-10-10; code unchanged)

**Separate authority from transport granularity.** The server owns effective datapack/custom metadata, validates appearance choices and permissions, and chooses NPC appearance. This does **not** imply that clothing or hair metadata must be pushed as separate updates to every client on every edit. MCA's clothing and hair render layers resolve texture IDs; the `VillagerLike` tracked values identify an entity's selected appearance. Eye rendering has a stronger client metadata dependency: `FaceLayer` reads `ClientAppearanceCatalog.eyeDefinition(...)` to composite/tint eyes. The editor and Skin Library also read catalog metadata. The local patched Minecraft 1.21.1 `SynchedEntityData` sends changed entity values, while `PlayerList` distributes complete recipe data on join/reload; neither pattern mandates an incremental packet protocol for this particular global MCA catalog.

**Proposed choice: retain a single `AppearanceCatalogSync` full-snapshot protocol.** Keep the existing six server-derived maps and the Fabric/NeoForge join and datapack reload hooks. After an authorized global clothing/hair add, meaningful replacement, or removal, reuse `AppearanceCatalogSync.sendToAll(server)` **once**, from the validated server-side mutation path, not `Storage#setDirty()`. Never send after denied input, an identical replacement, or a missing removal. Clients replace the catalog, including when no editor is open; preserve on-login/logout clearing to avoid old-server state. Do not reconstruct missing entries from bundled client data after receiving a server snapshot. Preserve custom-over-datapack precedence (one effective clothing entry per ID), explicit-over-generated hairstyle precedence, neutral gender behavior, canonical ID checks and validation.

**Simplification scope:** remove `AppearanceClothingUpdate`, `AppearanceHairUpdate`, their registration/handling, per-key client map patch methods and packet-only tests after rewriting the remaining tests to cover full snapshots and actual edit outcomes. Keep the existing `SkinCache`/`DynamicSkinCache` ownership of texture downloads and source-texture replacement. Do not replace metadata sync with a texture-transfer system. Full-sync cache invalidation may be less selective than incremental updates; first establish whether the broad stitched/eye-cache resets are observably expensive. Prefer a small, correct owner-level guard for unchanged eye definitions over another networking/cache framework if needed; preserve eye invalidation on real eye/resource changes.

**Release gates and fallback:** measure the serialized six-map snapshot for ordinary and supported large datapacks against NeoForge 1.21.1's 1 MiB clientbound payload limit; compare edit latency/cache rebuild impact under representative load. Verify Fabric and NeoForge with two clients (including one outside the editor), add/replace/delete, server switch, join while editing, datapack override removal, and `/reload`. If snapshots are too large or edits materially disrupt rendering, revisit narrowly scoped incremental updates using measured evidence; the existing incremental code is available as a reference. An oversized *join* snapshot cannot be fixed merely by per-edit packets. Do not claim multiplayer correctness from JUnit/build results.

**Decision boundary:** this is a proposed change to the previously approved/implemented design, **not an instruction to discard the uncommitted incremental work immediately**. Do not start the removal/refactor until the revised implementation plan is accepted. The previous sections remain a record of how that version was built and tested.

## Original incremental design (historical implementation record)

## Intended outcome

Keep every connected player's appearance metadata consistent with the server, including while another player edits global custom clothing or hair. Avoid rebuilding and broadcasting all six appearance maps on every edit. Preserve server-defined datapacks, the gender-neutral category, live editor/library refreshes, eye appearance behavior, and the existing client texture ownership. No client-side reconstruction of a server catalog from bundled defaults.

Successful behavior: joining/reloading still installs a complete authoritative catalog; an actual edit transfers only its affected server-resolved entries to **all** connected players, including those without a screen open; removing an override restores the server's effective datapack entry where one exists; unrelated entries and eye-generated textures stay intact.

## Source findings and historical failure modes

- On this branch, `AppearanceCatalogSync.current(server)` constructs clothing, body-skin, layered-hair, hair-style, custom-hair and eye maps. Fabric's `SYNC_DATA_PACK_CONTENTS` and NeoForge's `OnDatapackSyncEvent` send full snapshots on join/reload.
- `CustomClothingManager.Storage#setDirty()` sends `AppearanceCatalogSync.sendToAll` for every add/remove, including absent removals and equivalent replacements. `ClientHandlerImpl#handleAppearanceCatalogSync` then clears generated eye textures **and** the full stitched-skin cache and refreshes any open editor/library.
- `origin/1.21.1` already included `ClientSkinCatalog.mergeCatalogs()` plus `CustomSkinListRequest.delta()`. History: `d30d2d846` (server-to-bundled delta), `37b82eedc` (client merge); `a970e53be` intentionally replaced this with a server-authoritative six-map snapshot in the eye branch. `origin/1.21.1` is already an ancestor; no Git merge is needed.
- The old 'delta' was *effective server data compared to bundled built-ins*, **not** an incremental edit. It sent only server-present entries: it could not express removal of an entry present in the client baseline. It assumed compatible bundled defaults and used partial equivalence predicates (`sameClothing` omitted chance; `sameHairStyle` omitted exclude), risking stale metadata. Its lazy refresh also left non-editor clients with stale catalog metadata. Do not restore `BuiltInSkinCatalog`/`ClientSkinCatalog`, `installServerDelta`, or those comparators.
- New client `ClientAppearanceCatalog` is intentionally replaced in full from server data. Its `BUILT_IN` maps are only a temporary disconnected/pre-sync fallback. `HairStyleList.getAllStyles(customHair)` gives explicitly defined datapack styles precedence over generated custom-hair styles. `DynamicSkinCache.invalidateSourceTexture(ResourceLocation)` already selectively evicts stitched textures/faces whose `SkinKey` references the ID; `SkinCache` uses it when an actual library image loads.
- The server's full snapshot explicitly overlays custom clothing on datapack clothing, while the existing `ClothingList.allClothing()` concatenates both sources for selection and `SkinVisualIds.getKnownClothing()` checks datapack entries first. **Fix this as part of the implementation:** use the same custom-over-datapack precedence for selection, ID lookup and transmitted catalog. An override must contribute one effective entry to weighted pools, not a duplicate; removing it restores the datapack definition. Preserve current selection filtering and neutral-gender behavior.
- `AddCustomClothingMessage` validates a canonical `immersive_library:<integer>` ID, but `RemoveCustomClothingMessage` currently validates only permissions. `MCAClient.onLogout()` resets the catalog; `onLogin()` currently does not.

## Reference pattern and why it fits

- In patched Minecraft 1.21.1 sources, `PlayerList` sends complete recipes on join and recipes/tags after resource reload; `ServerScoreboard` sends individual score updates/removals, and `PlayerAdvancements.flushDirty` sends additions, removals and changed progress rather than rebuilding everything for each update.
- The local MineColonies 1.21.1 source sends a colony view to new subscribers and dirty view components, individual changed citizens via `ColonyViewCitizenViewMessage`, and explicit removals via `ColonyViewRemoveCitizenMessage`. This illustrates the **snapshot + keyed update + removal** pattern, not an API MCA should copy.
- MCA's appearance definitions are global shared metadata used by renderers even with the editor closed. Unlike a colony view, they have no existing subscriber ownership; broadcast small confirmed edits to all current players rather than introducing subscription bookkeeping.

## Options considered

1. **Full snapshot after each edit:** correct and minimal code, but repeated six-map serialization/broadcast and unrelated renderer invalidation. Retain only for join/reload.
2. **Old built-in-baseline diff plus lazy refresh:** fewer payloads during idle periods, but relies on client defaults and can leave other viewers stale. Rejected.
3. **Full snapshot on join/reload; small authoritative per-edit updates:** immediate client consistency, no general-purpose diff engine, and no baseline assumptions. **Selected.**

## Data and ownership contract

The server remains the sole authority. Retain `AppearanceCatalogSync` with the same six fields and existing Fabric/NeoForge join/datapack hooks; do not change its established codec or client full-replacement semantics.

For clothing, one effective ID has one effective definition across `AppearanceCatalogSync.current`, `ClothingList` selection/editor pools, and `SkinVisualIds` lookup. Resolve a copy of the datapack map with server custom entries overlaid by ID; never mutate the datapack map and never concatenate duplicate definitions. A client-only/disconnected call must preserve its existing built-in fallback behavior without inventing server custom metadata.

On a **successful** server-authorized mutation, the existing `AddCustomClothingMessage` or `RemoveCustomClothingMessage` handler dispatches one clientbound update through the shared `Network` API to every connected player. Use the handling player's `MinecraftServer` for both storage and broadcast, never a dummy storage fallback. No new loader hooks, polling, request/response round-trip, persistent revision map, timer, batching subsystem, or independent per-player cache.

Use two type-safe payloads under `network/s2c`:

| Packet | Fields | Server-derived meaning |
| --- | --- | --- |
| `AppearanceClothingUpdate` | `String identifier`, `Optional<Clothing> effectiveClothing` | Custom entry if present, otherwise effective `ClothingList.clothing` entry for the same ID; empty means remove the key |
| `AppearanceHairUpdate` | `String identifier`, `Optional<Hair> customHair`, `Optional<HairStyle> effectiveStyle` | Custom hair entry if present, plus explicit `HairStyleList.styles` entry if present, otherwise `HairStyle.fromHair(customHair)` if present; empty means remove that key |

Use `ByteBufCodecs.STRING_UTF8` and `ByteBufCodecs.optional(existing STREAM_CODEC)` with symmetric codecs; register both payloads as clientbound in `MessagesMCA`. An update contains only the affected key and its final **server** values. On a collision, the server's derived style or datapack clothing fallback is transmitted; the client never guesses it. `Optional.empty()` is an explicit deletion, *not* an instruction to substitute client built-ins. The hair packet updates `hair` and `hairStyles` together, so a dropped custom-hair entry also removes its generated style unless the server has an explicit style with that ID.

Mutation owner: `CustomClothingManager.Storage.addEntry(String,T)` and `removeEntry(String)` return `boolean changed`, returning false for semantically identical `toJson()` data or absent IDs. Only actual changes set `SavedData` dirty. Remove the network side effect from the `setDirty()` override; the validated network handlers are the currently identified edit entry points and dispatch notifications only when a storage operation returns true. The server builds the resolved packet **after** mutation from existing authoritative data, not by echoing client JSON. Retain addition permission/ID/JSON-size checks and apply the same existing canonical library-ID validation to **removals**, before touching storage. No packet for rejected input.

Client owner: add `ClientAppearanceCatalog.applyClothingUpdate(String, Optional<Clothing>)` and `applyHairUpdate(String, Optional<Hair>, Optional<HairStyle>)`. Each updates only its respective map keys using copy-on-write (`Map.copyOf`); do not merge client bundled maps or modify body skins, layered hair, or eyes. Validate the key and any present entry's internal ID before application; reject malformed hair/style pairs as a unit without partially updating either map. An update received before the initial server snapshot is ignored; it must already be represented in the later authoritative snapshot under the server's ordered send path. `MCAClient.onLogin()` and logout clear the previous session's readiness and maps, while the next full snapshot marks them ready. Do not reset readiness on a later datapack full snapshot; replace the maps and continue receiving edit packets. Client handlers use the existing main-thread dispatch, notify `AppearanceCatalogUpdateListener` for open screens after successful application, and apply packets even with no screen open.

Cache invalidation: for each valid changed clothing/hair key, use `DynamicSkinCache.invalidateSourceTexture(ResourceLocation.tryParse(identifier))` so stitched skins and face icons referencing the source are evicted. **Do not** clear `FaceLayer`'s generated eye textures for custom clothing/hair metadata edits. Retain the current broad cache resets on full join/datapack snapshots and actual client resource reloads; optimizing those is a separate question. A library *image* update remains owned by `SkinCache` and its existing texture-replacement path.

## Ordering, failures and scope boundaries

- Treat the vanilla connection's ordered clientbound stream as the delivery order: server handles edits on its game thread and sends updated values afterwards. A full snapshot must represent all edits sent **before** it, while edits sent **after** it must be applied after it on that connection. Verify this during join and `/reload` races; if a legitimate change can be lost, resolve that concrete ordering defect before release, not by assuming ignored pre-bootstrap packets are harmless. No revision or pending-retry protocol without evidence of an ordering failure.
- Do not emit a change for a denied/invalid edit, no-op replacement, or absent removal. Reject noncanonical removal IDs with the same ID predicate already used for additions; no separate identifier format. Clear stale catalog state when beginning a new connection as well as on disconnect.
- A datapack reload may add, replace, or remove arbitrary definitions in all six categories. Therefore it always triggers the **full** server snapshot, not per-entry custom updates. The client's maps are replaced, never incrementally reconciled against a guessed baseline.
- The custom-content payload is metadata, not texture PNG bytes; the existing Immersive Library image-download/invalidation path stays unchanged.
- Keep existing `Gender.NEUTRAL` behavior intentionally unchanged. No cosmetic editor redesign, unrelated Java cleanup, new worktree, code port, commit, or push.
- NeoForge 1.21.1 documents a **1 MiB clientbound custom-payload limit**: [version-specific payload documentation](https://docs.neoforged.net/docs/1.21.1/networking/payload/). Small edit updates reduce repeated traffic but do **not** solve an oversized initial snapshot. Measure representative full snapshots; if a supported pack exceeds the limit, stop and design a separately reviewed chunked/bootstrap protocol rather than ship a silent truncated catalog.

## Acceptance and test evidence required

1. Pure/minecraft-aware JUnit: add/new value, identical replacement, changed replacement, missing removal, valid removal, and `SavedData` dirty semantics; no network on unchanged input; add/remove share canonical library-ID acceptance and rejection cases.
2. JUnit: client clothing update/override/fallback/removal and hair update/override/derived-style/removal preserve unrelated six-map content and neutral metadata; no client bundled-baseline resurrection.
3. JUnit: both stream codecs round-trip present and empty entries with their correct identifiers; invalid or mismatched IDs do not partially mutate client maps; applying before initial snapshot cannot make a bundled fallback authoritative; login/logout reset and a subsequent full snapshot restores readiness.
4. Cache tests: a clothing/hair update invalidates referenced stitched skins and face icons without clearing unrelated entries or generated eye layers. Existing `DynamicSkinCacheInvalidationTest` protects targeted invalidation.
5. Runtime: Fabric and NeoForge two-client add/change/delete (one client with editor closed), editor/library refresh, connection switch, join during edits, and `/reload` interleaved with edits and datapack overrides/removals; client and server converge even if sync and edit packets are close together. Verify missing/invalid removal is silent, and a changed texture with unchanged metadata still follows the existing image path.
6. Verify focused common JUnit, `:common:test`, both loader builds, `git diff --check`, and serialized snapshot sizes under realistic/large datapacks. No JUnit/build-only result is sufficient proof of multiplayer behavior.
7. JUnit + runtime: same-ID custom clothing overrides datapack clothing exactly once in selection pools and the authoritative snapshot, including changed gender/profession/exclude/chance; removing custom content restores the datapack entry. Unrelated clothing remains available; neutral behavior is unchanged.
