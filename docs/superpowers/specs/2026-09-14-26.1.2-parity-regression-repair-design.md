# MCA 26.1.2 Parity Regression Repair Design

**Status:** Draft for review  
**Date:** 2026-09-14  
**Target branch:** `dev/26.1.2`  
**Behavioral authority:** `dev/1.21.1`  
**Minecraft 26.1 API authority:** `C:\Users\Mik\Downloads\MCA\local-source\local-sources\minecraft-patched-26.1.2.76-sources`

## Purpose

Restore behavioral parity between MCA `dev/26.1.2` and the current `dev/1.21.1` authority without undoing intentional 26.1-specific adaptations.

The parity audit identified nine concrete regressions introduced or left incomplete by the 26.1 port, plus one newer authority-branch archer checkpoint that has not yet been ported. This design treats those ten items as the complete repair scope.

The implementation must preserve the 26.1 API model where it differs from 1.21.1. The goal is behavioral equivalence, not textual equivalence.

## Source-of-truth rules

For every change:

1. `dev/1.21.1` defines intended MCA behavior.
2. Patched Minecraft 26.1.2 sources define the legal target API and runtime semantics.
3. Existing target-specific fixes must survive unless they directly conflict with current authority behavior.
4. A source behavior may be adapted, but it must not be silently dropped.
5. Serialization is not an acceptable substitute for preserving live runtime state when the authority preserved live state.
6. Migration fixes must remain backward compatible with already-created 26.1 data as well as pre-port 1.21.1 data.

## Scope

### Required repairs

| # | Severity | Area | Problem |
|---|---|---|---|
| 1 | HIGH | Inworld AI | Child/relative romantic-attraction safeguards and relative context were dropped. |
| 2 | HIGH | FamilyTree migration | Legacy `MCA-FamilyTree.dat` is never probed after the SavedData ID rename. |
| 3 | HIGH | Procreation | `INFERTILE` no longer blocks the married-player `procreate` command path. |
| 4 | HIGH | Recovery food | Recovery eating can overwrite and destroy the villager's equipped dominant-hand item. |
| 5 | MEDIUM | Brain refresh | `brain.pack()` drops live codec-less memories; guard FOLLOW transitions can lose combat state. |
| 6 | MEDIUM | Destiny teleport | A permanent level-32 `PLAYER_LOADING` ticket pins destination chunks. |
| 7 | MEDIUM | Tombstones | Namespaced/custom registered tombstone configuration falls back incorrectly. |
| 8 | MEDIUM | Player dimensions | Scaled server hitboxes are not explicitly refreshed/synchronized on join. |
| 9 | LOW | Greeting history | Newly-created `Memories.lastSeen` uses game time instead of the overworld clock. |
| 10 | HIGH parity gap | Archer combat | Current `dev/1.21.1` commit `4493a7af1` is not yet adapted to 26.1. |

### Explicitly out of scope

- JourneyMap compatibility is not treated as a regression in this repair. Modern JourneyMap 26.x was shown to obtain living-entity icons through the renderer texture path, which MCA 26.1 already supplies with its stitched skin.
- Trade-set `amount: 2.0` is parity-correct with vanilla's two offers per villager level.
- Replacing `MixinEntityType` with `MixinTypedInstance`, removal of `MixinSynchedEntityData`, data-driven item model migration, Fabric reload-listener wrappers, and current class-tweaker/pathfinding adaptations are already validated target adaptations.
- This repair must not broaden behavior beyond current `dev/1.21.1` merely because later or unrelated branches contain additional changes.

## Design principles

### Prefer invariant-preserving helpers over one-off exceptions

The current `PLAYER_FOLLOWING` special case in `refreshBrain()` demonstrates why preserving one known transient memory at a time is fragile. The repair should preserve the relevant live brain memory set generically rather than extending a growing whitelist every time another dropped memory is noticed.

### Preserve existing target safety work

The following target behavior must survive:

- `LookAtTargetSink` danger gating.
- MCA climb/navigation vertical velocity handling.
- Target pathfinding/class-tweaker widenings still required by 26.1.
- Fishing chore combat-weapon preservation through `clearChoreItem`.
- Data-driven item/render migrations required by 26.1.

### Test behavioral contracts, not implementation shape

Regression tests should assert externally meaningful invariants: no lost item, no permanent ticket, no lost combat target, correct relationship scoring, successful legacy migration, correct collision dimensions, and correct archer movement ownership. They should not merely assert that a particular helper method was called.

## 1. Restore Inworld child/relative romantic safeguards

### Problem

Authority commit `22b9ba11c` changed `RelationshipModule.updateRelationship()` so Inworld-provided `flirtatious` and `attraction` values do not affect relationship hearts when the villager is a BABY, TODDLER, CHILD, or a relative of the player. It also added relative context to `RelationModule`.

Current 26.1 directly sums `update.flirtatious()` and `update.attraction()` and omits the relative-context prompt.

### Required behavior

- Preserve Inworld's non-romantic relationship updates.
- Treat `flirtatious` and `attraction` as zero when the villager is BABY, TODDLER, or CHILD.
- Treat `flirtatious` and `attraction` as zero when `Relationship.IS_RELATIVE` is true.
- Add the authority relative-context sentence to `RelationModule` so the model receives the same family context.
- Do not alter the existing OpenAI safeguards; they already provide equivalent protection through their own prompt path.

### Acceptance criteria

- An adult, unrelated villager still applies Inworld attraction/flirtation normally.
- A child-age villager cannot gain or lose hearts from the romantic Inworld fields.
- A relative cannot gain or lose hearts from the romantic Inworld fields.
- Other Inworld relationship dimensions still apply in all three cases.
- Relation context explicitly states when villager and player are related.

## 2. Preserve live brain memories across `refreshBrain()`

### Problem

Authority used `brain.copyWithoutBehaviors()`, preserving the old brain's live memories while rebuilding behavior packages.

The 26.1 port rebuilds through `brain.pack()` and restores only `PLAYER_FOLLOWING`. In 26.1, `Brain.pack()` serializes only memory modules with codecs. Codec-less live memories therefore disappear, including MCA memories such as:

- `PLAYER_FOLLOWING`
- `NEAREST_GUARD_ENEMY`
- `HIT_BY_PLAYER`
- `RANGED_COMBAT_STATE`

and vanilla live memories including:

- `ATTACK_TARGET`
- `LOOK_TARGET`
- `WALK_TARGET`

This is especially visible when commanding an active guard to FOLLOW: current 26.1 refreshes the brain and can interrupt the current fight, whereas authority explicitly avoids that refresh and restores the combat walk/look target.

### Required behavior

- Brain refresh must preserve live memory values independently of NBT/codec serializability.
- Do not solve this by adding more individual hard-coded memory exceptions.
- Use a target-compatible equivalent of `copyWithoutBehaviors()`: preserve the old brain's registered live memories, rebuild/rebind behavior packages, then continue with the same live state.
- If 26.1 exposes no direct whole-brain copy operation, introduce an MCA helper that snapshots and reapplies the registered live memory modules used by the villager brain profile. The helper must include both MCA and vanilla modules and must not route through `Brain.pack()` for the live-state copy.
- Match authority `setMoveState(FOLLOW, leader)` semantics for guards:
  - set `PLAYER_FOLLOWING`;
  - do not perform a destructive brain refresh for FOLLOW;
  - preserve active `ATTACK_TARGET`;
  - preserve/restore target-facing `LOOK_TARGET` and combat `WALK_TARGET` when the target remains alive and in the same level.

### Acceptance criteria

- `refreshBrain()` preserves values in codec-less MCA memory modules.
- `refreshBrain()` preserves `ATTACK_TARGET`, `LOOK_TARGET`, and `WALK_TARGET` when they were live before refresh and remain valid.
- Switching an actively fighting guard to FOLLOW does not end or reset the fight.
- A guard's ranged combat state is not reset merely because its profession/brain packages are refreshed.
- Existing `PLAYER_FOLLOWING` and STAY/MOVE transitions still work.
- Saved brain serialization remains valid; live-memory preservation does not require making transient memories serializable.

## 3. Restore legacy FamilyTree migration

### Problem

Port commit `31d057d7e` changed the current FamilyTree SavedData ID from `MCA-FamilyTree` to `family_tree`. The generic legacy fallback is passed the new ID and consequently probes `family_tree.dat`, never the real pre-port file `MCA-FamilyTree.dat`.

### Required behavior

- Keep the current 26.1 namespaced SavedData ID `family_tree` for newly saved data.
- Load current-format data first.
- If current-format data does not exist, explicitly probe the legacy ID `MCA-FamilyTree` using the existing legacy-data mechanism.
- Once legacy data has been read, expose it through the normal current FamilyTree instance so subsequent saves use the 26.1 ID.
- If both current and legacy data exist, current data wins. Do not merge two family trees automatically.
- Do not change IDs for other SavedData classes.

### Acceptance criteria

- A world containing only legacy `MCA-FamilyTree.dat` loads all family relationships on 26.1.
- That world subsequently saves current `family_tree` data.
- A world containing current `family_tree` data continues to load unchanged.
- When both forms exist, current data is selected deterministically.
- No duplicate or split FamilyTree instances are created.

## 4. Restore infertility enforcement for player-triggered procreation

### Problem

Authority `VillagerCommandHandler` checks `Traits.INFERTILE` before starting the `procreate` interaction. Current 26.1 skips that check.

This is not only a dialogue regression. The married-player interaction starts `BreedableRelationship.startProcreating()`, records cooldown, and later calls `Pregnancy.procreate(spouse)` directly. That path does not pass through `tryStartGestation()` and therefore does not re-check infertility.

Natural/cake gestation already remains protected by `Pregnancy.tryStartGestation()`.

### Required behavior

- Restore the authority infertility guard in the `procreate` command before cooldown/start.
- Return the infertility failure interaction response used by authority.
- Ensure the failed attempt does not start the 60-tick procreation sequence and does not consume/reset the procreation cooldown.
- Do not alter the existing `tryStartGestation()` infertility checks.
- Do not broaden this repair into unrelated fertility mechanics.

### Acceptance criteria

- An infertile married villager cannot produce a baby through the player `procreate` command.
- An infertile command attempt does not consume cooldown.
- The player receives the infertility-specific failure message.
- Fertile married villagers still use the existing command/cooldown flow.
- Natural/cake gestation behavior remains unchanged.

## 5. Restore the recovery-food state machine without item loss

### Problem

Authority contains a full recovery-food lifecycle that saves/restores the previous dominant-hand item, performs actual item use over time, renders eating feedback, and cancels use when danger appears.

Current 26.1 can split food from inventory and replace the dominant-hand slot directly. Patched 26.1 `LivingEntity.setItemInHand()` ultimately overwrites that equipment slot. The old weapon/tool is not automatically preserved and can be silently destroyed.

### Required behavior

Port the authority recovery-food lifecycle to 26.1 item-use APIs while preserving target-specific combat behavior.

The state machine must:

1. Decide whether recovery can begin only when the villager is hurt and not currently in danger.
2. Preserve the previous dominant-hand stack before equipping inventory food.
3. Move exactly one recoverable food item into the use hand when sourced from inventory.
4. Use the normal 26.1 item-use duration/consumption path rather than applying an instant custom substitute.
5. Produce the authority eating animation/particles where supported by 26.1.
6. Cancel recovery when combat/panic/guard danger becomes active.
7. On completion or cancellation, restore the previous dominant-hand stack exactly once.
8. Never overwrite or delete a combat weapon/tool.
9. Preserve the target `clearChoreItem` combat safety and do not conflate chore equipment with recovery-food restoration.

### Acceptance criteria

- A villager holding a sword can recover using inventory food and still holds the same sword afterward.
- Cancelling recovery because an enemy appears restores the previous held item and does not double-consume food.
- Recovery consumes exactly one food item on successful completion.
- Recovery does not start while the villager is in active danger.
- Eating uses normal item-use timing/feedback rather than silently healing in one step.
- Existing guard/ranged combat equipment selection remains intact.

## 6. Replace permanent Destiny `PLAYER_LOADING` tickets with expiring teleport tickets

### Problem

Current `DestinyMessage` calls:

`addTicketWithRadius(TicketType.PLAYER_LOADING, chunkPos, 1)`

In patched 26.1:

- `PLAYER_LOADING` has timeout `0`, meaning no timeout.
- radius `1` maps to ticket level `32` (`FULL` level 33 minus radius 1).
- vanilla player loading uses `PLAYER_LOADING` at entity-ticking level `31`.
- `TicketStorage` considers tickets identical only when both type and level match.

Therefore vanilla cleanup of its level-31 player ticket cannot remove MCA's level-32 ticket, and MCA never explicitly removes it. The destination chunk can stay permanently loaded.

Authority used `POST_TELEPORT`, which had a five-tick timeout. 26.1 no longer exposes that vanilla ticket type.

### Required behavior

- Do not use `PLAYER_LOADING` for one-shot Destiny teleport preparation.
- Define/register an MCA-specific loading ticket type for Destiny/post-teleport use with:
  - loading capability;
  - no simulation requirement unless target teleport behavior proves it necessary;
  - **5-tick timeout**, matching the old authority `POST_TELEPORT` lifetime.
- Add that ticket at the destination with radius `1`, preserving the current pre-teleport chunk-loading reach.
- Repeated additions for the same type/level should refresh the existing ticket lifetime under 26.1 `TicketStorage` semantics rather than accumulate independent permanent tickets.
- The teleport itself must continue only after the destination has been prepared as currently required.

### Acceptance criteria

- Destiny teleport still loads the destination sufficiently for a safe teleport.
- The MCA Destiny ticket exists immediately after the teleport request.
- The ticket expires after its five-tick lifetime and no longer pins the destination chunk.
- Repeated teleports do not leave an increasing set of permanent tickets.
- No `PLAYER_LOADING` ticket is introduced by MCA's Destiny path.

## 7. Restore registry-based tombstone configuration

### Problem

Authority `Relationship.getConfiguredTombstoneState()` resolves `Config.defaultHeadstoneType` through the block registry, adds the `mca:` namespace when the config uses a short ID, accepts any registered `TombstoneBlock`, and falls back to the cross headstone.

Current 26.1 uses `BlocksMCA.BLOCKS.get(configValue)`, which only supports MCA's internal short-name map. Namespaced IDs and externally registered tombstone blocks silently fall back.

### Required behavior

- Parse the configured value as a 26.1 `Identifier`/registry key.
- When the value has no namespace, default it to `mca:` for backward compatibility with existing config values.
- Resolve through the 26.1 block registry rather than `BlocksMCA.BLOCKS`.
- Accept the block only when it is a `TombstoneBlock`.
- Fall back to the cross headstone for malformed IDs, missing blocks, or non-tombstone blocks.
- Do not change the configuration key or its ordinary default value.

### Acceptance criteria

- `cross_headstone` resolves to MCA's cross headstone.
- `mca:cross_headstone` resolves identically.
- A registered third-party namespace containing a `TombstoneBlock` is accepted.
- A valid registered non-tombstone block falls back safely.
- A malformed/unknown ID falls back safely without crashing.

## 8. Restore join-time scaled hitbox refresh and sync

### Problem

When `scalePlayerHitboxWithSizeAndWidth` is enabled, authority `ServerInteractionManager.onPlayerJoin()` explicitly refreshes player dimensions and synchronizes customized player data.

Current 26.1 removed that block. In patched 26.1, the base `Entity` constructor caches dimensions from the `EntityType`; MCA's `MixinLivingEntity.getDimensions` only affects the cached server hitbox when dimensions are recalculated. A joining customized player can therefore remain at vanilla server collision dimensions until some unrelated later refresh.

### Required behavior

- When `scalePlayerHitboxWithSizeAndWidth` is disabled, preserve current join behavior with no extra work.
- When enabled:
  1. ensure `PlayerSaveData`/MCA entity customization state is available;
  2. call the target 26.1 dimension-refresh API on the joining `ServerPlayer`;
  3. if MCA entity data has been set, broadcast/synchronize that data to the relevant connected players using the current 26.1 network layer.
- Preserve any current lazy client request behavior; the explicit join sync is a correctness guarantee for the enabled hitbox feature, not a replacement for all client data requests.
- Match current `dev/1.21.1` join behavior. Do not add unrelated respawn behavior unless it is separately present in the authority being ported at implementation time.

### Acceptance criteria

- With the config disabled, join dimensions remain vanilla and no redundant MCA dimension refresh is required.
- With the config enabled and non-default MCA player size/width, the server collision box is correct immediately after join.
- Other connected clients receive the customized player data required to render/interpret the player consistently.
- Rejoining does not leave stale dimensions from a previous/default state.

## 9. Use the overworld clock for newly-created greeting memories

### Problem

`Memories` stores `lastSeen` in days by dividing the constructor's time value by `24000`.

Current `VillagerBrain.getMemoriesForPlayer()` constructs a new record with `player.level().getGameTime()`, while:

- `Memories.fromCNBT()` uses `getOverworldClockTime()`;
- `GreetPlayerTask` uses `getOverworldClockTime()` for comparisons and updates;
- authority used day time for both creation and greeting logic.

Minecraft 26.1 world clocks can be moved independently of monotonic game time. New memories can therefore begin on a different day basis from all future comparisons.

### Required behavior

- Construct new `Memories` with `player.level().getOverworldClockTime()`.
- Keep `Memories.lastSeen` stored as the day index (`clockTicks / 24000`).
- Keep existing serialized `lastSeen` values unchanged.
- Do not convert cooldowns or unrelated monotonic timers from `getGameTime()`; this repair applies only to calendar/day semantics.

### Acceptance criteria

- A newly created memory's `lastSeen` equals the current overworld-clock day.
- `/time`/sleep-adjusted world-clock changes do not create an artificial greeting delay or immediate stale greeting caused by game-time mismatch.
- Existing saved memories continue using their stored day value unchanged.

## 10. Port `4493a7af1` archer combat movement checkpoint to 26.1

### Problem

Current `dev/1.21.1` has advanced with production commit:

`4493a7af1 Checkpoint archer combat movement`

It is not contained in `dev/26.1.2`. This is a current parity gap rather than a defect in the already-completed merge.

The checkpoint changes movement ownership and escape behavior across:

- `MCAMoveControl`
- `ArcherMovementTask`
- `BowTask`
- `RangedCombatPositioning`
- archer unit/GameTests

### Required behavior

Port the checkpoint semantically to the 26.1 movement/navigation APIs. Preserve all existing target-specific pathfinding fixes.

Required contracts include:

1. **Combat movement ownership**
   - Emergency flee can replace a stale/pre-combat `WALK_TARGET`.
   - Direct strafe mode explicitly claims direct movement and stops stale navigation before issuing strafe input.
   - Combat code may replace its own old walk target without being blocked by ownership bookkeeping.

2. **Group-aware kite escape**
   - KITE evaluates nearby movement threats as a group, not only one threat.
   - A chosen retreat must not increase safety from one threat by closing on another visible/nearby threat.
   - KITE must not fall back to an emergency candidate that violates group safety.

3. **Raised escape candidates**
   - Group escape search can choose a valid one-block-higher walkable surface when that is the only safe lane.

4. **Normal movement speed**
   - KITE path speed uses the normal approach speed (`0.5`) rather than the older accelerated `0.85` retreat speed.
   - Bow drawing while navigation owns movement must not issue a direct strafe command that overwrites the current move-control speed.
   - 26.1 `MCAMoveControl` must support the checkpoint's explicit strafe-speed semantics where required.

5. **Facing ownership**
   - `BowTask` must not directly override locomotion yaw while drawing.
   - Archer movement/brain retains attack-target look ownership while navigation controls body yaw.
   - Vanilla head/body yaw limits remain respected.

6. **Strafe cadence**
   - Match authority checkpoint timing constants: hold before strafe `10`, strafe duration `24-40`, cooldown `20-40`.

### Acceptance criteria

- Port/adapt the checkpoint's archer unit tests and GameTests to the 26.1 GameTest compatibility layer.
- The authority cases for pre-combat walk-target replacement, group kite escape, group fallback rejection, raised escape candidate, bow-facing ownership, navigation speed, path speed, and updated strafe cadence all pass.
- Existing 26.1 raised-path/trapdoor handling and `LookAtTargetSink` danger safety continue to pass their prior tests.

## Cross-cutting test strategy

Implementation should proceed TDD-first for each workstream: add the smallest regression test that demonstrates the authority contract, observe it fail on current `dev/26.1.2`, then implement the 26.1 adaptation.

### Common/unit coverage

Prefer common tests for pure behavior that does not require a live level:

- relationship-field filtering;
- tombstone ID parsing/validation where registries can be supplied safely;
- `Memories` day calculation;
- archer positioning helpers/state transitions where existing unit tests already cover them.

### NeoForge GameTests

Use GameTests for live world/entity/chunk behavior:

- recovery-food item preservation and danger cancellation;
- guard FOLLOW while actively fighting;
- FamilyTree migration if the SavedData test harness can represent old files reliably; otherwise use a focused persistence integration test;
- Destiny ticket expiry;
- scaled player collision dimensions where a suitable server-player fixture exists;
- full archer movement contracts from `4493a7af1`.

Maintain the existing 26.1 per-batch GameTest environment isolation. Do not reintroduce isotropic padding hacks.

### Required verification after all fixes

At minimum:

```text
.\gradlew :common:test --console=plain
.\gradlew :neoforge:runGameTestServer --console=plain
.\gradlew compileJava processResources --console=plain
.\gradlew build --console=plain
git diff --check
```

Also verify:

- no unresolved conflict markers;
- no production GameTest/compatibility registrar classes leak into the NeoForge distribution jar;
- no intentional target class-tweaker/pathfinding fix disappears;
- the implementation base still accounts for the current production head of `dev/1.21.1` before declaring parity complete.

## Migration and compatibility requirements

- Existing 26.1 saves must continue to load.
- Pre-port 1.21.1 FamilyTree saves must migrate.
- Existing config short names for tombstones must continue to work.
- No new persistent Destiny ticket state may be introduced.
- Existing serialized `Memories.lastSeen` values must not be rewritten merely because the clock source for new memories changes.
- Live transient brain memories remain runtime-only; do not make them persistent solely to solve refresh loss.

## Recommended implementation order

1. FamilyTree migration and Destiny ticket lifetime, because both affect persistent/runtime world resources and have narrow contracts.
2. Greeting clock and tombstone registry lookup, because both are small isolated semantic corrections.
3. Inworld safety and infertility, because both restore explicit gameplay/safety authority behavior with narrow call paths.
4. Brain refresh/FOLLOW semantics, because this changes shared AI state ownership and should land before the archer checkpoint.
5. Recovery-food state machine, preserving the repaired brain/combat invariants.
6. Player join dimensions/sync.
7. Archer checkpoint `4493a7af1`, after the shared brain/movement invariants are stable.
8. Full common/GameTest/build/package verification.

## Definition of done

The repair is complete when all of the following are true:

- Every one of the ten scoped workstreams has an evidence-backed regression test or adapted authority test.
- The nine confirmed port regressions are fixed without undoing 26.1-specific adaptations.
- `4493a7af1` behavior is adapted and covered on 26.1.
- All focused tests, common tests, required NeoForge GameTests, compilation, and full build pass.
- Production jars contain no test-only compatibility classes/resources.
- The worktree diff contains no unrelated refactoring.
- A fresh `dev/1.21.1` head check shows no additional unported production commits before parity is declared complete.
